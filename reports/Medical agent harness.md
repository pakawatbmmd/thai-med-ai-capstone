# Make the Harness the Experiment, Not the Product

**Yes: a medical-domain agent harness is a feasible and defensible 9-month capstone on a 16 GB laptop, but only in a narrower form than "build a medical harness".** The headline novelty claims ("no one has built a medical harness", "first to show the harness matters in medicine") are already false as of October 2026. Northwestern's MedicalHarness (5 Oct 2026) crossed 6 harnesses with 5 local open models on 107 medical tasks and decomposed the variance: **model 58%, harness 12%, harness × model interaction 12%, seed noise 18%** ([MedicalHarness](https://arxiv.org/html/2610.05778v1)). Harvard's Asclepius (Sep 2026), Microsoft's MAI-DxO (2025) and Stanford's MedAgentBench v2 (2026) already treat the harness as the thing being improved. The evidence that a harness changes results with the model held fixed is solid: mature harness swaps move scores **3–17 points** and token cost by **10–100×**. The honest counterpoint is equally solid: model choice usually matters more ([Terminal-Bench 2.0](https://arxiv.org/html/2601.11868v1)). What remains open, and what a single student can own, is a **controlled, model-held-fixed ablation of the safety-enforcing parts of a medical harness**: deterministic hooks, code-keyed Thai terminology tools, escalation gates and abstention. It would run on **Thai-locale clinical tasks with small on-prem Thai models**, measuring unsafe actions, over-escalation and cost alongside accuracy. No harness study found so far is in Thai or any Southeast Asian language. None of them isolates guardrail or escalation components against unsafe-action metrics, and Thailand's legal and IT context (PDPA, no national terminology server, the Medical Council's "AI only supports, the doctor decides") makes exactly those components the ones that matter. This framing also reuses most of the student's current "audit-first" plan: the audit benchmark becomes the evaluation harness, and the rule-based verifiers become runtime hooks. The main risks are clinician-validated ground truth, run-to-run noise that swamps small effects, and the fact that the easiest Thai harness tasks (coding audit, claims pre-check) look like the "safe admin" ideas the student has already rejected.

## A harness is the hospital system around the doctor, not the doctor

The definitions literature converged in 2025–2026 on a simple formula: **agent = model + harness**. The harness is "the software infrastructure surrounding a large language model that enables it to operate as an AI agent": the loop, tool dispatch, memory and state, sandbox, context management and guardrails ([Wikipedia: Agent harness](https://en.wikipedia.org/wiki/Agent_harness)). An academic version calls it "the external execution system around a model that organizes a task run". The same paper complains that harness logic is usually "buried in tightly coupled controller code", which makes it hard to compare and ablate ([Natural-Language Agent Harnesses](https://arxiv.org/abs/2603.25723)). Anthropic calls its own Agent SDK "a general-purpose agent harness" ([Anthropic, long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)). The older academic word is "scaffold", which goes back to the UK AI Safety Institute in 2023 and is used by SWE-agent and HAL. "Harness engineering" became a named practice in early 2026 through LangChain, Thoughtworks/Martin Fowler and O'Reilly ([LangChain](https://langchain.com/blog/improving-deep-agents-with-harness-engineering); [Wikipedia](https://en.wikipedia.org/wiki/Agent_harness)).

For the committee, the most useful definition is an operational one. **The harness is every non-weight, run-time choice that decides what the model sees and what its outputs are allowed to do.** That covers six swappable parts: the control loop, the tools and their interface, context and memory policy, state, verification and permissions, and instructions. Because each part can be changed while the weights stay frozen, the harness is a manipulable independent variable. That is what makes it research rather than plumbing.

The vocabulary the student asked about maps onto this as components, packaging or products, not as alternatives to a harness. Claude Code's documentation is explicit. Skills are on-demand markdown instructions. Output styles (the nearest thing to a "mode") set role, tone and format. Hooks run deterministic scripts at lifecycle events "without Claude deciding". **Plugins "are the packaging layer"** that bundle skills, hooks, subagents and MCP servers ([Claude Code docs](https://code.claude.com/docs/en/features-overview)). The table translates each term for both halves of the committee.

| Term | Engineer's definition | Clinician analogy | Relation to the harness |
|---|---|---|---|
| **Model** | Trained weights that map tokens to tokens | The clinician's trained knowledge and judgement | Not part of the harness; the thing the harness wraps |
| **Harness** | Loop + tools + context policy + state + checks + instructions | The hospital system around the clinician: chart, formulary, order sets, pharmacist verification, referral pathway | The object of study |
| **Prompt / system prompt / CLAUDE.md** | Text loaded into context every run | A poster on the ward wall, or standing orders | Instruction component (probabilistic) |
| **Skill** | Markdown workflow loaded on demand | A CPG pocket card pulled out when the situation arises | Instruction component (probabilistic) |
| **Mode / output style** | Session-wide role and format setting | Which hat you wear: triage nurse vs consultant writing a referral letter | Instruction component |
| **Hook / permission gate** | Code that runs at a lifecycle event and can block an action | A CPOE hard stop that refuses a contraindicated order | Deterministic control component |
| **MCP server / tool** | A protocol that exposes external functions and data | Lab, pharmacy and radiology services the clinician can call | Tool component |
| **Subagent** | A separate loop with isolated context that returns a summary | A consult to another service that sends back a note | Orchestration and context component |
| **Plugin** | An installable bundle of the above | A service-line kit, e.g. a stroke fast-track bundle (protocol + order set + alert) | Distribution, not a component |
| **App** (Claude Code, ChatGPT Health) | One specific harness plus UI, accounts and distribution | A whole hospital building with a front desk | A harness productised |
| **Agent framework** (LangGraph, smolagents) | A library for building harnesses | The architecture firm and building codes | A toolkit for harnesses |
| **Evaluation harness** (Inspect, HAL, Harbor) | Infrastructure that runs and grades agents | The accreditation inspector's audit protocol | Measures the agent; not part of it |

The single sentence that persuades clinicians comes from Claude Code's own documentation: "An instruction like 'never edit .env' in CLAUDE.md or a skill is a **request, not a guarantee**. A PreToolUse hook that blocks the edit is enforcement" ([Claude Code docs](https://code.claude.com/docs/en/features-overview)). In hospital terms, a prompt is a poster and a hook is a hard stop. A Thai deployment has already shown why the difference matters. The TSWAP wellness chatbot's backend model produced "a full drug-dosing schedule" once its safety prompt was removed. The safety lived in the harness, and in its weakest, probabilistic form ([TSWAP](https://arxiv.org/abs/2608.22917)).

This also clarifies why "harness instead of a model or an app" is a real choice. Building a *model* means changing weights: fine-tuning, RL, the student's earlier RSI direction. Building an *app* means owning a user-facing product: UX, deployment, accounts and, in medicine, Software as a Medical Device (SaMD) exposure. Building a *harness* means building the model-agnostic layer in between. Its research value appears only when it is evaluated as a variable, with the model held fixed and swapped. A harness thesis that never swaps components or models is an app thesis in disguise.

### The "big factory vs small infantry section" analogy holds, with two repairs

The student's analogy contrasts Claude Code, a general-purpose "factory" with many tools, heavy context and broad capability, with a small, specialised "infantry section". The evidence supports its core intuition. On Terminal-Bench 2.0, Claude Opus 4.5 used **256.9M input tokens in Claude Code vs 3.9M in the one-tool Terminus 2 harness**, yet scored *lower* in Claude Code (52.1% vs 57.8%) ([Terminal-Bench 2.0](https://arxiv.org/html/2601.11868v1)). Small models are especially hurt by factory-scale tool catalogues. Tool-selection accuracy rose from **13.6% to 43.1%** when only relevant tool schemas were shown ([RAG-MCP](https://arxiv.org/abs/2505.03275)). In MedicalHarness, hiding tools behind a search step caused misnamed tool calls in **95 of 96** MedTool episodes for Qwen ([MedicalHarness](https://arxiv.org/html/2610.05778v1)). A harness built for small local models (Mingbird) scored **0.886 vs 0.405–0.631** for general harnesses on the same 2–35B models, while frontier models in well-formed scaffolds landed within 0.072 of each other ([Mingbird](https://arxiv.org/abs/2610.02001)).

Two repairs make the analogy committee-proof. First, the winning axis is **fit to model and task, not smallness**. HAL found task-specific scaffolds beat its generalist scaffold in 9 of 12 same-model runs on CORE-Bench Hard ([HAL](https://arxiv.org/html/2510.11977)). A generalist with a small, general toolset, OpenHands-Versa, beat specialist multi-agent systems on three benchmarks ([OpenHands-Versa](https://arxiv.org/abs/2506.03011)). MedicalHarness found "no single harness is best across all models and tasks". Second, an infantry section's real advantage is **doctrine**: rules of engagement, a fixed kit list and a radio to headquarters. In harness terms those are deterministic hooks, a curated toolset and an escalation path to a clinician. Soldiers still matter, though. The model explains most of the variance, and a harness cannot rescue a model below a capability floor. A version that clinicians will recognise immediately is **a well-run รพ.สต. (sub-district health-promoting hospital)**, not a tertiary hospital. It has limited staff and kit, but standard protocols, and it knows exactly when to refer up.

## Same model, different harness: 3–17 points, but the model still wins

The strongest committee-proof evidence is Terminal-Bench 2.0 (ICLR 2026). It ran 6 agent harnesses × 16 models with at least 5 runs per cell and 95% confidence intervals of about ±2–3 points. Same-model spreads across harnesses reached **16.9 points for Gemini 2.5 Pro** (32.6% in Terminus 2 vs 15.7% in OpenHands), **16.5 for Claude Haiku 4.5** and **15.7 for GPT-5** (49.6% in Codex CLI vs 33.9% in Mini-SWE-Agent). For other models the spread was inside the noise: 2.7 points for Claude Sonnet 4.5 and 0.4 for Qwen3 Coder 480B ([Terminal-Bench 2.0](https://arxiv.org/html/2601.11868v1)). A vendor's own harness was not reliably best for its own model. Gemini 2.5 Pro scored 13 points lower in Gemini CLI than in the one-tool Terminus 2. Engineered improvements show the same magnitude. LangChain moved GPT-5.2-Codex from **52.8% to 66.5% (+13.7 points)** by changing only the prompt, tools and middleware. The core fix was a forced verification pass before the agent may exit, because the commonest failure was the agent "re-reading its own code, confirming it looked fine, and stopping" ([LangChain](https://langchain.com/blog/improving-deep-agents-with-harness-engineering)).

Component-level evidence is older but cleaner. SWE-agent's ablations with GPT-4 Turbo held fixed show the shell-only agent at **11.0% vs 18.0%** for the full agent-computer interface. Removing the edit command cost 7.7 points, and removing the lint guardrail on edits cost 3.0. An "iterative search" tool scored 6 points *worse* than having no search tool, because agents read every match exhaustively ([SWE-agent](https://arxiv.org/abs/2405.15793)). Less agentic can win as well: Agentless, a fixed localise-repair-validate pipeline, reached **32% on SWE-bench Lite at $0.70** per issue, beating contemporary open agents ([Agentless](https://arxiv.org/abs/2407.01489)). On cost, simple observation masking **halved cost** at equal or better solve rate compared with LLM summarisation ([The Complexity Trap](https://arxiv.org/abs/2508.21433)). An MIT FutureTech analysis of HAL data reports inference efficiency varying "by up to **100x** between scaffolds" ([Just a Wrapper?](https://www.lesswrong.com/posts/jXLi3dhSpSMd7B6z8/just-a-wrapper-how-much-do-scaffolds-matter-1)). Late-2026 controlled studies show the effect depends on the context budget. Context management was worth about **+35.7 points at a 32k window but only +2.7 at 128k** on SWE-Bench across four models. Planning helped weaker models' accuracy but mainly cut cost for stronger ones ([Fan et al.](https://arxiv.org/abs/2609.20804); numbers via [agentpatterns.ai](https://agentpatterns.ai/patterns/agent-design/task-shape-harness-payoff/)). That matters directly for a 16 GB laptop, which runs at 8–32k context.

Medicine shows the same pattern. MAI-DxO, a model-agnostic orchestrator built as a virtual physician panel, raised off-the-shelf models by **7.9 points on average** on NEJM cases. It took o3 from **78.6% at $7,850 per case to 81.9% at $4,735**, lifted Gemini 2.5 Flash by 24.4%, and added only about 3–5 points to the strongest models. On MIMIC-IV-ED the gain fell to 4.4%, and Gemini 2.5 Pro did not improve ([Nori et al., Nov 2025](https://erichorvitz.com/sequential_diagnosis_LM.pdf); [arXiv 2506.22405](https://arxiv.org/html/2506.22405v1)). Asclepius improved critical actions by **+25% (p<0.001)** and timeliness by 13%, while diagnosis was flat (−0.02, n.s.). On held-out batches only critical actions stayed significant ([Asclepius](https://arxiv.org/html/2609.13543)). This is the medical harness signature: **harnesses move process, safety and cost more reliably than diagnostic accuracy**. A generic harness can also hurt. Vanilla OpenManus on a Llama-4 backbone *lost* 3.3 points on AgentClinic-MedQA and 12.5 on NEJM image-by-request while using more than 10× the tokens. A medically customised prompt-plus-tools variant gained 8.9 ([Kather lab, npj Digit Med 2026](https://pmc.ncbi.nlm.nih.gov/articles/PMC13031301/)).

The counterpoint must be conceded up front, because the committee's engineers will know it. The Terminal-Bench authors conclude that "model selection is usually more important than agent scaffold". Under one fixed harness, models ranged from **3.1% to 57.8%**, far wider than any harness spread ([Terminal-Bench 2.0](https://arxiv.org/html/2601.11868v1)). MedicalHarness puts the model at 58% of variance against 24% for harness plus interaction ([MedicalHarness](https://arxiv.org/html/2610.05778v1)). Harness gains shrink as models improve. OpenHands' margin on SWE-bench Verified fell from +13.6 to +5.5 points between Claude 3.7 Sonnet and Claude 4 Sonnet ([Hu et al.](https://arxiv.org/abs/2609.32459)). One blog claims Terminal-Bench 2.1 spreads shrink to 0.2–8.1 points once reasoning effort and submission date are matched ([Vaughan](https://codex.danielvaughan.com/2026/06/11/terminal-bench-2-1-june-2026-benchmark-landscape-codex-cli-harness-engineering-model-scores/)). The defensible thesis claim is therefore not "harness beats model". It is this: **the harness is a measurable second factor with strong model interactions, and it is the factor a Thai hospital can actually control.** PDPA and on-prem constraints cap model size, and the harness is the only place where enforceable safety can live.

The prior-art landscape rules out three tempting claims and leaves three narrower ones open. The table lists the work any proposal must cite and position against.

Three claims are now off the table: "first medical agent harness", "first to show the harness matters in medicine", and "first harness × model comparison on medical tasks". MedicalHarness alone defeats all three. The literature also undercuts "multi-agent is better" (MedAgentBoard; AgentRx found single agents beat naive multi-agent systems on multimodal clinical prediction, [AgentRx](https://arxiv.org/html/2605.10286v1)), and it undercuts "more tools is better".

Three narrower claims remain open as far as these searches reached. The first is **locale**: every harness study found is English and US-centric, built on NEJM, MIMIC, CMS and US price tables. None uses a Thai formulary, Thai coding systems or Thai-language small models. The second is **safety-component ablation with safety outcomes**. MedicalHarness ablates capability mechanisms, and Asclepius reports critical actions. Nobody isolates permission gates, contraindication checks, red-flag escalation or abstention against unsafe-action, over-escalation and escalation-correctness metrics. The Symbolic Guardrails paper comes closest and must be cited as the direct predecessor. The third is the **"poster vs hard stop" contrast**: the same safety rule delivered as prompt text versus as a deterministic hook, crossed with model size. Practitioner docs assert this difference, but no controlled medical measurement was found. A defensible novelty sentence would read: *"to our knowledge (searches to October 2026), the first controlled, model-held-fixed ablation of deterministic safety components in a clinical agent harness, on Thai-locale tasks with on-prem Thai models."* The field moves weekly. MedicalHarness appeared 16 days before this report, so a novelty re-check belongs in month 1 and again before submission.

## Thailand forces the harness to carry terminology, privacy and escalation

Thai clinical IT pushes work into the harness rather than the model, for structural reasons. Public-hospital data mostly sits in vendor databases. BMS HOSxP runs in "over 300 hospitals" and has **no public, documented clinical API**; its "API Gateway" is a login page ([Wikipedia: HOSxP](https://en.wikipedia.org/wiki/HOSxP); [BMS API Gateway](https://cloud4.hosxp.net/)). The portable data contract is the MOPH **43-file (43 แฟ้ม) standard** feeding the Health Data Center ([MOPH BDH slides](https://bdh.moph.go.th/site/wp-content/uploads/2023/10/ห้องย่อย-3-22Aug2023-2.pdf)). SIL-TH's **MoPH-PC-1 FHIR implementation guide** maps it to FHIR, and the Claimcon IG maps claim datasets to FHIR across 8 medical schools ([SIL-TH IGs](https://www.fhir-ig.sil-th.org/)). FHIR is voluntary, mostly R4, and Thailand has **no national FHIR terminology server and none planned** ([Simplifier: Thailand](https://simplifier.net/jurisdictions/th)). Since 1 April 2024, UC claims must flow through MOPH's Financial Data Hub (FDH) as the only channel ([PPTV](https://www.pptvhd36.com/health/news/5144)).

The national code systems a harness needs are all locally maintained. The Thai Medicines Terminology (TMT) is released roughly every two weeks (latest **TMTRF20261019**, behind a free login). TMLT covers labs, though no public TMLT–LOINC crosswalk was found ([THIS TMT](https://this.or.th/service/tmt/); [AeHIN](https://asiaehealthinformationnetwork.org/?p=2656)). ICD-10-TM and Thai DRG drive inpatient payment ([TDRG v6.2](https://medinfo.psu.ac.th/medrec/mediplus-lite/uploads/TDRGVersion6.2V1.pdf)). With no terminology server, **the harness must bundle its own versioned, offline terminology service**. This is a harness argument, not a model argument: no model will memorise a biweekly drug registry. Drug-interaction knowledge is contested even among commercial databases. On HIV antiretrovirals, Drugs.com flagged 302 pairs, Liverpool 222 and Micromedex 160 ([SJST/PSU](https://sjst.psu.ac.th/index.php/article/168/PaperPDF/download)). A DDI tool must therefore cite its source rather than assert a single truth.

Thai models' tool use is the weak link that harness components target. The best documented Thai function-calling scores come from a **machine-translated** Thai BFCL: Typhoon2-Qwen2.5-7B 75.1, Typhoon2-Llama-8B 74.2 and OpenThaiGPT1.5-7B 65.5. Roughly one call in four fails even on generic tools ([Typhoon 2](https://arxiv.org/html/2412.13702v1)). Laptop-sized candidates include Typhoon2.5-Qwen3-4B (Apache-2.0, function calling, 256k context) ([HF](https://huggingface.co/scb10x/typhoon2.5-qwen3-4b)) and Pathumma-llm-text-4.0.0 (4.5B, claims Thai/English tool use; dates unverified) ([Featherless](https://featherless.ai/models/nectec/Pathumma-llm-text-4.0.0)). ThaiLLM-8B-ToolUse reports 0.999 accuracy, but only for routing among 8 app tools ([card](https://huggingface.co/ThaiLLM/ThaiLLM-8B-ToolUse)). No native-Thai or clinical-Thai tool-use benchmark exists. Two harness design rules follow. The first is to use **grammar-constrained decoding**, which takes schema validity from 78.6–92.9% to 100% in sub-4B models while leaving semantic errors untouched ([Chavan](https://arxiv.org/abs/2609.23742)). The second is to make tool arguments **code-keyed** (a TMT ID or ICD code) rather than free Thai text, with the tool resolving the Thai display name. Thai tokenisation is fragile: 4-bit AWQ quantisation corrupted Thai tone marks in TSWAP ([TSWAP](https://arxiv.org/abs/2608.22917)), and renaming tools to match small models' pretraining conventions cut schema-misalignment errors by 80% ([PA-Tool](https://arxiv.org/abs/2510.07248)). The risk of Thai tokenisation breaking JSON tool calls is a hypothesis; no published study measures it.

The rules point the same way. Health data is sensitive under PDPA s.26 ([Private AI](https://www.private-ai.com/en/blog/thailand-pdpa)). The PDPC's July 2026 draft healthcare guideline asks for **DPIAs for AI-enabled healthcare applications** and focuses on cross-border cloud transfers ([HLC](https://hlc.com/en/publications/thailand-pdpc-consults-on-first-healthcarespecific-data-protection-guideline)). The non-binding PDPC AI guideline v1.0 (7 Oct 2026) advises on-prem deployment when sensitive data is involved ([TRAINIAC](https://www.trainiac.ai/blog/ai-in-healthcare-thailand)). MOPH and the Medical Council's stated position is that **"แพทย์ยังคงเป็นผู้ตัดสินใจหลักในการรักษา ส่วน AI เป็นเพียงเครื่องมือช่วยสนับสนุน"** (doctors remain the main decision-makers; AI is only a support tool), and they name lab-result analysis and triage as target uses ([Hfocus, Oct 2025](https://www.hfocus.org/content/2025/10/35551)). Thai FDA regulates software by intended medical purpose, with SaMD guidance from June 2024 (revised October 2024) ([ThaiJO JAM](https://so02.tci-thaijo.org/index.php/jam/article/view/287392)). UDI labelling for SaMD took effect on **20 June 2026** ([Tilleke & Gibbins](https://www.tilleke.com/insights/thailand-introduces-udi-labeling-requirements-for-software-as-a-medical-device/8/)). Each of these maps onto a harness component: human sign-off hooks, audit logs of tool calls, de-identification before any model call, no outbound network by default, and versioned terminology snapshots. A model cannot implement any of them; a harness can. An offline research harness evaluated on synthetic cases with no patient contact is low-risk, but SaMD status turns on intended purpose and is not a legal conclusion here.

The Thai failures that motivate a safety harness are already documented. ThaiLLM-27B-Prescreen has **F1 = 0 for "Observe at Home"**: it never recommends home care. TMA-1 scores **27% or lower on drug–drug interactions** ([Prescreen card](https://huggingface.co/ThaiLLM/ThaiLLM-27B-Prescreen); [TMA-1 4B](https://huggingface.co/icdevelop/tma1-medgemma-4b)). The candidate tasks below are ranked by how well they isolate harness effects, how cheaply ground truth can be built, and how they fit the student's stated taste.

|---|---|---|---|---|
| 1 | **Medication safety**: normalise Thai/English/brand drug lists to TMT, check dose and route, flag DDIs with cited sources, escalate | Lookup-then-verify, code-keyed output, deterministic dose and DDI hooks; targets TMA-1's ≤27% DDI weakness | Mostly deterministic (TMT IDs, dose tables); DDI needs pharmacist adjudication | Moderate; matches the student's Option A |
| 2 | **Symptom triage and red-flag escalation** (1669 / Criteria Based Dispatch-style protocol cards) | Escalation hook, protocol retrieval, abstention; directly tests over- vs under-triage (Prescreen's failure) | Clinician-labelled vignettes (ESI/disposition); a KMUTT CBD decision tree reported 82% vs 70% for human triage ([KMUTT](https://kirim.kmutt.ac.th/converis/portal/detail/Publication/1504627774?lang=en_GB)) | Higher (closer to SaMD; needs an ER partner); matches Option B |
| 3 | **Structured referral/discharge into MoPH-PC-1 FHIR** | FHIR validator, terminology tools, completeness checker | Validator plus clinician review of free text | Low; complements PresScribe-style scribes ([Microsoft](https://news.microsoft.com/source/asia/features/bangkok-medical-software-utilizes-presscribeai-by-looloo-health-to-enhance-healthcare-services-across-35-hospitals-in-thailand/)) |

## A single student can run a 4-model × 7-arm factorial if they budget for noise

The evaluation must separate two harnesses that are easy to confuse: the **agent harness under test** and the **evaluation harness** that runs and grades it. UK AISI's Inspect fits the second role. A task is dataset + solver + scorer, `eval()` takes `epochs` and `sandbox` arguments, and **the solver is the swappable harness**, which makes model × harness factorials a configuration change ([Inspect](https://inspect.aisi.org.uk/reference/inspect_ai.html)). The 2026 standard is a fully crossed model × harness design. It uses matched settings, repeated trials, paired per-task statistics, outcome-state verification, and cost reported alongside accuracy as a Pareto frontier ([HAL](https://arxiv.org/html/2510.11977)). Component effects come from **leave-one-in / leave-one-out ablations on a minimal base harness**. That is the right method because every component is two-edged: compression cost −4.9 points in one study ([Hu et al.](https://arxiv.org/abs/2609.32459)), and a search tool cost 6 points in SWE-agent.

A design that fits the laptop uses the following harness arms, each a frozen configuration of one codebase.

| Arm | Contents | What it isolates |
|---|---|---|
| H0 bare | ReAct loop, native function calling, no domain tools | Floor: the model's own knowledge |
| H1 +tools | Small curated toolset (e.g. `tmt_search`, `dose_check`, `ddi_check` with source) | Domain tool value |
| H2 +constrained | H1 + JSON-grammar decoding + code-keyed arguments | Structural tool-call failures (schema vs semantic, reported separately) |
| H3-prompt | H2 + safety rules written as system-prompt text | "Poster" |
| H3-hook | H2 + the *same* rules as deterministic pre/post tool hooks (block, escalate, require sign-off) | "Hard stop": the core contrast with H3-prompt |
| H4 full | H3-hook + finish/verification gate + rule-based context elision | Full medical harness |
| G general | One off-the-shelf general harness (e.g. a mini-SWE-agent- or opencode-style loop) with H1's tools | "Factory vs infantry" |

The model factor should have at least two capability tiers, because the interesting quantity is the **harness × model interaction**. A practical set is two or three local models plus one API reference. The local candidates are Typhoon2.5-Qwen3-4B, Pathumma-4.5B, an 8B Thai model such as ThaiLLM-8B-MedApp v2 (check its licence), and a generic non-Thai control such as Qwen3-4B. Typhoon2.5-30B-A3B, at about 17–19 GB in Q4, needs CPU offload and is the laptop's ceiling (an inference from the notes; not measured). The API reference model runs only on synthetic data, which keeps PDPA out of play. Runtime confounds must be fixed and logged: inference engine, quantisation level and chat template. No study was found that controls them, and they plausibly change tool-call formats.

Metrics should be reported side by side, never collapsed into one score. Primary are **task success** (deterministically graded against the outcome state, not the agent's claim) and **unsafe-action rate**: the share of trajectories with at least one executed policy-violating action. Next come the guardrail trade-off measures used in AgentDojo-style evaluation: block precision and recall, **over-blocking/over-escalation**, and **escalation correctness** on a balanced should-escalate/should-not set ([ToolSafe](https://arxiv.org/abs/2601.10156); [Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Over-escalation matters most clinically, because the cheapest way to zero unsafe actions is to "send everyone to the ER", which is exactly Prescreen's failure. Then **pass^3**, the probability that all three trials succeed. GPT-4o's retail success fell about 60% from pass^1 to pass^8 on τ-bench ([τ-bench](https://arxiv.org/abs/2406.12045)). Also report the **answer-production rate**, because MedicalHarness found harnesses differ mainly in whether an episode ends with any answer at all. Cost metrics are tokens, latency and GPU-hours (dollars for the API arm). Finally, add a **component-fired check**, because agents often ignore the interface they were assigned, so unverified comparisons "measure an unknown mixture" ([Alier Forment et al.](https://arxiv.org/abs/2608.08654)).

Statistics are where single-student harness studies usually fail. MedicalHarness found **18% of variance was seed noise (40% on planning tasks)**. In Mingbird, same-night replications moved an arm's mean by up to 0.069, as large as the single-trial deltas, and only a batch-matched three-replication comparison gave a credible +0.10 for completion guards ([Mingbird](https://arxiv.org/abs/2610.02001)). The design therefore needs k = 3–5 epochs per task, paired per-task comparisons, and clustered standard errors (they can exceed naive ones by more than 3×) ([Miller, Adding Error Bars](https://arxiv.org/abs/2411.00640)). Averaging repeated generations per item raises power because prediction noise usually exceeds data noise ([Wang](https://arxiv.org/abs/2512.21326)). The main analysis is a mixed-effects logistic model with task as a random effect and arm × model as fixed effects, with Holm correction across arms. As a back-of-envelope estimate, about 250 tasks × 3 epochs should resolve paired differences of roughly 6–9 points, so effects smaller than that are not worth designing arms for. A power analysis on month-1 pilot data (e.g. with the `errorbars` package, [PyPI](https://pypi.org/project/errorbars/)) should replace this estimate. Validity rules round out the design. Freeze the harness before touching a **held-out 30% split**; LangChain, Meta-Harness and the hashline study all tuned and tested on one benchmark. Grade with code wherever possible. Use LLM judges only for free text, calibrated against clinicians with an "unknown" exit, because GPT-4-as-judge could not tell wrong GPT-4 chemistry answers from ChemCrow's ([ChemCrow](https://arxiv.org/abs/2304.05376)). Apply the Agentic Benchmark Checklist, since task and reward flaws misestimate agent performance by up to 100% ([ABC](https://arxiv.org/abs/2507.02825)). And read the transcripts.

Compute is not the bottleneck. As a rough estimate, 4 models × 7 arms × 250 tasks × 3 epochs is 21,000 episodes. At about 60 seconds per episode unbatched, that is roughly 350 laptop-hours. With vLLM batching at 8 concurrent episodes, it falls to roughly 50–100 hours. Either fits in a 9-month plan; a fractional design (full arms on two models, H0/H3-prompt/H3-hook/H4 on the rest) halves it. Labels are the bottleneck. Anthropic's guidance that "20–50 simple tasks drawn from real failures is a great start" sets the month-1 scale ([Anthropic evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). The final set needs about 250 items, with a clinician-validated subset of at least 50 and an inter-rater agreement statistic. A realistic schedule: month 1 for the novelty re-check, a 50-task pilot and the kill test; months 2–3 for building tools, hooks and the task set with the partner; month 4 to freeze the harness and run pilot power; months 5–6 for the full factorial; month 7 for transcript analysis and the clinician-graded subset; months 8–9 for writing and release.

## Five framings for the council, ranked

The ranking weighs four criteria: defensible novelty against MedicalHarness and Symbolic Guardrails, deterministic ground truth, fit with the student's existing audit-first plan and partner options, and frontier appeal. All five share the evaluation design above; they differ in task, emphasis and risk.

| Rank | Framing | One-line research question | Best if the partner is |
|---|---|---|---|
| 1 | **Poster vs hard stop: Thai medication-safety harness** | Do deterministic safety hooks reduce unsafe medication actions more than the same rules as prompts, and does the gap widen for smaller Thai models? | Pharmacist |
| 2 | **Red-flag escalation harness for Thai symptom triage** | Which harness components cut under-triage without inflating over-triage? | ER/triage clinician |
| 3 | **Verifier as hook vs verifier as reward** | For the same rule-based verifiers, is inference-time enforcement or RSI training better, and do they compose? | Either (stretch) |
| 4 | **Thai MedAgentBench on MoPH-PC-1 FHIR** | How much do structured Thai terminology tools and constrained decoding move small-model success on Thai EHR tasks? | Informatics / medical records |
| 5 | **Factory vs infantry** | Does a minimal domain harness beat general agent harnesses for small Thai models on accuracy per token? | Any (sub-study) |

### 1. Poster vs hard stop: a Thai medication-safety harness

This is the top pick because it owns the cleanest open gap, the prompt-vs-hook contrast measured on safety outcomes, and its ground truth is largely deterministic. The TSWAP and TMA-1 failures give it a ready Thai motivation, and it is the student's Option A recast as a harness study.

| Field | Content |
|---|---|
| Research question | With the model held fixed, how much do deterministic pre/post tool hooks reduce executed unsafe medication actions compared with identical rules given as prompt text? What does it cost in over-blocking and utility, and does the hook advantage grow as model size falls? |
| Components to ablate | H0–H4 as above; the H3-prompt vs H3-hook contrast is primary; secondary: constrained decoding, toolset size (5 vs 15 tools) |
| Task/data | About 250 synthetic Thai medication tasks: drug lists in Thai, English and brand names to normalise to TMT; dose, route and before/after-meal (ก่อน/หลังอาหาร) checks; DDI pairs only where sources agree or a pharmacist adjudicates; a balanced set with no-action cases; 30% held out |
| Models | Typhoon2.5-Qwen3-4B, Pathumma-4.5B, one 8B Thai model, generic Qwen3-4B control, one API reference |
| Metrics | Unsafe-action rate (primary), block precision/recall, over-blocking, task success, pass^3, tokens/latency, component-fired rate |
| Key risk | Clinically "hard" DDI ground truth is contested (302/222/160 database disagreement); TMT licence terms for research use unchecked; Symbolic Guardrails may be seen as already covering it, so the Thai locale and prompt-vs-hook contrast must carry the novelty |
| Month-1 kill test | Build 50 tasks and run H0, H3-prompt and H3-hook on two local models × 3 epochs. **Kill or pivot if** the bare unsafe-action rate is already below 5% (nothing to fix), if hooks cut unsafe actions by less than 10 points or cost more than 10 points of utility, or if no pharmacist will validate the 50 items by week 4 |

### 2. A red-flag escalation harness for Thai symptom triage

This framing has the highest clinical salience and matches the student's preferred Option B. It also turns Prescreen's "never home" failure into a measurable over-triage axis. It ranks second only because labels need an ER partner and it sits closer to SaMD.

| Field | Content |
|---|---|
| Research question | Which harness components (deterministic red-flag escalation hook, protocol-card retrieval, abstention gate, structured disposition output) reduce under-triage, and at what over-triage cost, across Thai models of different sizes? |
| Components to ablate | Escalation hook vs prompt rule; protocol retrieval on/off; abstention/"refer" tool; finish gate; general harness G |
| Task/data | About 250 Thai vignettes (lay register, some dialect) labelled for disposition/ESI and 1669 referral by two clinicians; balanced red-flag and benign cases; CBD-style protocol cards as the knowledge tool |
| Models | Same tiers as framing 1; ThaiLLM-27B-Prescreen as an external reference model only if it fits (likely needs offload or the API arm) |
| Metrics | Under-triage of red flags (primary), over-triage, escalation correctness, weighted kappa vs clinician panel, answer-production rate, cost |
| Key risk | Label reliability; the safety-vs-over-triage trade-off may show the hook simply escalating everything; closer to SaMD intended-purpose concerns |
| Month-1 kill test | Two clinicians label 60 vignettes. **Kill or switch to framing 1** if no ER partner by week 4, if inter-rater weighted kappa is below 0.6, or if every arm (including H0) already escalates all red flags so that only over-triage varies |

### 3. Verifier as hook vs verifier as reward

This framing bridges the harness idea and the student's existing RSI plan, which gives it the most "frontier" character. The question is whether the same rule-based verifiers are worth more as runtime hooks or as training reward. It is a stretch goal, because it doubles the engineering.

| Field | Content |
|---|---|
| Research question | Given verifier A, does enforcing it at inference (harness hook) or training against it (GRPO + QLoRA self-play) give better held-out safety on verifier B and a clinician set? Do they compose, and which one reward-hacks or over-escalates first? |
| Components to ablate | 2×2: hook {off, on} × RSI-trained {no, yes}, plus H3-prompt |
| Task/data | Framing 1 or 2 task set; verifier A for hooks and reward, verifier B and clinician items for evaluation only |
| Models | One 1.5–4B model trained (e.g. Qwen3-4B or a Thai 4B) and its untrained twin; the API model as reference |
| Metrics | Verifier-B pass, clinician-set safety, over-escalation, cost per correct answer (inference tokens vs GPU-hours of training) |
| Key risk | Scope: a harness plus an RSI pipeline in 9 months; the earlier council estimated 120–220 GPU-hours for a comparable RSI run ([council v3](../full_council_v3_frontier.md)) |
| Month-1 kill test | If H3-hook alone reaches 95% or more on verifier B with acceptable over-escalation, the RSI arm has no headroom; collapse to framing 1 or 2 and report that as a finding. Also drop the RSI arm if measured GRPO rollout throughput on the laptop cannot finish 3 rounds within 150 GPU-hours |

### 4. Thai MedAgentBench on MoPH-PC-1 FHIR

This framing produces the most reusable infrastructure: a Thai analogue of Stanford's FHIR environment. It ranks fourth because building the environment eats the schedule and the tasks drift toward the admin work the student rejected.

| Field | Content |
|---|---|
| Research question | On Thai EHR query/action tasks, how much do structured Thai terminology tools (TMT/ICD-10-TM/FHIR validator), code-keyed arguments and constrained decoding improve small-model success, and how does context policy interact with 8–32k windows? |
| Components to ablate | Raw HTTP vs structured FHIR tools; constrained decoding; context elision at 8k/16k/32k; finish tool; memory |
| Task/data | A HAPI-style FHIR server loaded with about 100 synthetic patients shaped to MoPH-PC-1; about 200 tasks adapted from MedAgentBench templates ([GitHub](https://github.com/stanfordmlgroup/medagentbench)) |
| Models | Same tiers |
| Metrics | Task success (state-verified), schema validity vs semantic correctness, tokens, context-overflow rate |
| Key risk | Synthetic-data validity; engineering time; perceived as admin |
| Month-1 kill test | Stand up the server with 30 patients and 30 tasks. **Kill** if this is not running end-to-end with two models by week 4, or if H0 already exceeds 85% (no headroom) |

### 5. Factory vs infantry

This framing tests the student's analogy directly. Standalone it is the weakest, since MedicalHarness and Mingbird already compare harnesses on small models. It works best as a sub-experiment (arm G) inside framings 1 or 2.

| Field | Content |
|---|---|
| Research question | For small Thai models, does a minimal domain harness beat general agent harnesses on accuracy, answer production and tokens per correct answer, and does the gap close for the API model? |
| Components to ablate | Whole-harness swap: 2 general harnesses vs H4 vs H0, with identical tools exposed |
| Task/data | Framing 1 or 2 task set |
| Models | Same tiers |
| Metrics | Success, answer-production rate, tokens and latency per correct answer, harness × model interaction |
| Key risk | Low novelty; general harnesses may be hard to run against local models with identical tool exposure |
| Month-1 kill test | Run 30 tasks on Typhoon2.5-4B in two general harnesses and H4 × 3 epochs. **Drop as standalone** if the differences fall inside the replication noise; keep as arm G |

The council should debate one coupling explicitly. **Framings 1 and 2 are the same experiment with a different partner.** The decision on which KCMH clinician to recruit, pharmacist or ER, is therefore also the decision between them. Framing 3 is the add-on that answers "where is the frontier ML?". Framings 4 and 5 are fallbacks or sub-studies.

## Committee questions the student must answer before they're asked

| Likely question | Honest answer |
|---|---|
| "Isn't this just prompt engineering?" | No. Prompts are one of six components, and the core experiment shows where prompts fail: the same rule as prompt vs as a hook. Prompt engineering is a narrower layer inside harness engineering ([Wikipedia](https://en.wikipedia.org/wiki/Agent_harness)) |
| "MedicalHarness did this two weeks ago. What's new?" | They ablated capability mechanisms (summarisation, planning, tool search) on English US tasks. This work ablates safety-enforcing components with safety metrics on Thai tasks and Thai models, including over-escalation. It cites them as the baseline method, and can reuse their tasks if released |
| "If model choice matters more, why not just use the best model?" | Agreed that the model is the bigger factor (58% vs 24% of variance). But Thai hospitals face PDPA/on-prem pressure that caps model size, harness effects are largest for small models (MAI-DxO +24.4% on Gemini Flash vs about +3 on o3), and enforceable safety can only live in the harness. The thesis reports the interaction rather than claiming dominance |
| "Why not fine-tune a Thai model instead?" | Fine-tuning is the model factor and can enter the design as one more model (framing 3 makes it the comparison). ThaiLLM-8B-ToolUse already tuned routing; nobody has measured what wraps it |
| "Where is the patient benefit?" | The harness targets documented Thai failures: DDI ≤27%, never-home triage, and a dosing schedule once the safety prompt was removed. The output is an open, model-agnostic safety layer and benchmark that any hospital can wrap around any model, consistent with "AI supports, the doctor decides" |
| "Synthetic tasks aren't real patients." | True: external validity is limited and stated as such. Mitigations are a clinician-validated subset with inter-rater agreement, a balanced should/shouldn't-act design, and deterministic grading. No patient data also means no PDPA exposure for the API arm |
| "Isn't this a medical device?" | An offline research harness on synthetic cases with no patient contact is not being placed on the market. SaMD status turns on intended purpose, and Thai FDA guidance was not reviewed in full. A deployment would need that analysis |
| "How do we know you didn't tune the harness to your test set?" | Freeze the harness before evaluation, hold out 30%, pre-register hypotheses and arms, and release code, tasks and logs |
| "Your effects are within noise." | That is the main methodological risk. The design uses 3–5 epochs, paired tests, clustered SEs and a pilot-based power analysis, and does not interpret deltas below about 6–9 points |
| "A new model next month makes this obsolete." | The harness is model-agnostic, and the API reference arm measures whether gains shrink at the frontier. That shrinkage is itself a finding the literature predicts ([Hu et al.](https://arxiv.org/abs/2609.32459)) |
| "Where is the frontier ML? You rejected safe admin ideas." | Harness science is an active 2026 research front (Meta-Harness, NLAH, Harness-R1). Framing 3 adds RL. But honestly, this is empirical systems science, not a new architecture, and the coding/claims task variant would be the "safe admin" project wearing new clothes |
| "Why not integrate with HOSxP?" | HOSxP has no public clinical API. The harness targets the 43-file / MoPH-PC-1 data shape that every MOPH facility already exports, which is more portable than any single vendor integration |

## Conclusion

The question has shifted from "harness or model?" to "which safety guarantees can only a harness provide, and what do they cost?". The evidence makes the harness a real but secondary performance lever, and a first-order lever for cost, process and enforceable safety. Those are precisely the properties a Thai public-hospital deployment is constrained on, by PDPA, on-prem hardware and the Medical Council's insistence that a clinician decides. A capstone that measures the gap between a rule written as a poster and the same rule enforced as a hard stop answers a question practitioners assert but nobody has measured in medicine. Run on small Thai models with over-escalation counted as a harm rather than a safety win, it is novel in the narrow way that survives a committee. It does not need a better model, a hospital integration or a product.

Two strategic implications follow for the council. First, the harness framing and the existing audit-first plan are not competitors: the audit benchmark is the evaluation harness, and the two rule-based verifiers are the hooks. Adopting this framing therefore costs little of the work already planned and adds a cleaner experimental variable. Second, the choice of clinical partner now decides the project. A pharmacist leads to framing 1, with near-deterministic ground truth. An ER clinician leads to framing 2, with higher stakes and a harder label problem. Securing that partner in the first four weeks matters more than any architectural decision.
